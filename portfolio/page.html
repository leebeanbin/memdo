제품 관점

왜 채팅이 아니라 캘린더인가

사용자가 일부러 앱을 열고, 대화를 시작하고, 맥락을 다시 설명해야 하는 Agent는 결국 잘 안 쓰게 됩니다. Memdo는 Agent를 그 자리에 두는 대신, 이미 매일 보는 화면 위로 옮겼습니다.

처음엔 이 프로젝트에도 AI 전용 탭이 있었습니다. 하지만 실제로 써보니 탭을 하나 더 만드는 건 "Agent를 또 다른 대화창에 가두는 것"과 다르지 않았습니다. 그래서 AI 전용 페이지를 없애고, 오늘· 캘린더·설정 옆에 문맥형 Agent 액션만 남겼습니다(ADR-060) — 탭을 눌러 새 화면으로 이동하는 대신, 지금 보고 있는 일정 위에서 바로 제안을 받는 방식입니다.
이 방향을 지키기 위한 규칙도 하나 있습니다 — 일정 완료 여부는 AI가 추측하지 않고, 사용자가 정한 시간에 사용자의 응답으로만 바뀝니다. 반복 일정과 알림은 AI 없이도 완결된 기본 기능이고, AI는 계획 초안·자연어 입력·빈 시간 탐색처럼 선택적으로 쓰는 보조 도구입니다. Agent는 무엇이든 제안만 하고, 실제 쓰기는 항상 사용자가 승인한 뒤 일반 API를 통해서만 일어납니다.

새 일정

붙여넣기로 채우기

텍스트를 붙여넣으면 온디바이스 Agent가 제목·시간·장소를 채웁니다. 저장 전 값은 전부 수정 가능합니다.

일정 상세

낙관적 동시성

모든 수정은 version 필드로 충돌을 검사합니다. 재예약은 원본 종료와 새 일정 생성을 하나의 Postgres 함수로 묶은 원자적 command입니다.

캘린더

온디맨드 반복 일정

반복 일정을 미리 다 만들어두지 않고, 조회 시점에 필요한 발생분만 계산합니다. DST·월말·단일 예외까지 검증했습니다.

설정

연결은 명시적으로

Google Calendar·Slack 연결은 로그인과 분리된 별도 동의입니다. 실제 사용 범위(읽기·승인 후 쓰기)를 화면에 그대로 노출합니다.

Agent

제안만 하고, 쓰지 않는다

Agent는 조회와 제안까지만 합니다. 실제 저장은 사용자가 승인한 뒤 일반 Command API가 수행합니다.

동기화 흐름

지하철에서 일정을 수정해도 잃어버리지 않는 이유

오프라인 중 만든 변경이 재연결 후 서버와 안전하게 수렴하는 전체 경로입니다. iOS OutboxQueue.swift와 백엔드 sync Edge Function이 나눠서 맡습니다.

오프라인 상태에서 생성·수정·삭제

네트워크 요청이 실패하면 ScheduleAPIError.offline로 분류하고, 변경 내용을 버리지 않습니다.

OutboxStore actor가 디스크에 큐잉

작업을 JSON으로 직렬화해 로컬에 순서대로 저장합니다. 앱이 종료돼도 큐는 남습니다.

NWPathMonitor가 복귀를 감지

네트워크가 돌아오는 순간을 폴링이 아니라 이벤트로 받아, 불필요한 재시도를 하지 않습니다.

큐를 순서대로 재전송, 원래 Idempotency-Key 재사용

같은 요청이 중복 도착해도 서버가 같은 키로 한 번만 반영하도록, 큐에 넣을 때 만든 키를 그대로 씁니다.

서버가 idempotency·version으로 충돌을 검사

재연결 사이 다른 기기에서 먼저 바뀐 값이 있으면 409를 반환하고, 클라이언트는 무작정 덮어쓰지 않습니다.

재시도할 가치가 있는 실패만 큐에 남긴다

여전히 오프라인이면 그 자리에서 멈추고 나머지를 큐에 남깁니다. 서버가 실제로 거부한 요청(예: 충돌)은 큐에서 빼고 사용자에게 에러로 보여준 뒤 refresh()로 서버 상태와 다시 맞춥니다 — 의미 없는 재시도를 무한 반복하지 않습니다.

(updatedAt, id) 커서로 증분 반영

다음 sync 호출부터는 깊은 OFFSET 없이 바뀐 것과 삭제 tombstone만 내려받습니다.

트러블슈팅

실제로 겪고 고친 문제들

결과 화면보다 더 많은 시간을 여기에 썼습니다. 증상 → 원인 → 해결 순으로 정리했습니다.

01

로컬은 통과, CI는 실패하는 타임존 버그

증상

반복 일정 충돌 검사 테스트가 로컬(KST)에서는 통과하는데 GitHub Actions(UTC)에서는 실패했습니다.

원인

날짜 계산 함수가 setHours(로컬 타임존)와 toISOString()(UTC)을 섞어 썼습니다. 소스를 고친 뒤에도 테스트 픽스처가 오프셋 없는 문자열('2026-08-16T14:00:00')을 써서 같은 모호함이 재발했습니다.

해결

Date.UTC() + 명시적 분 단위 오프셋으로 재작성하고, 테스트 픽스처도 프로덕션 함수로 만들도록 바꿔 TZ=UTC/TZ=America/New_York로 교차 검증했습니다.

02

컴파일러가 엉뚱한 곳을 지목한 SwiftUI 에러

증상

운동 기록 편집 화면에서 ForEach·Range<Int> 관련 캐스케이딩 컴파일 에러가 났는데, 정작 그 코드는 건드리지 않았습니다.

원인

바로 위에 추가한 .frame(width: 76, minHeight: 64) 한 줄이 원인이었습니다. SwiftUI엔 이 조합의 frame 오버로드가 없어 타입 추론이 실패하며 엉뚱한 위치를 에러로 보고했습니다.

해결

.frame(width: 76).frame(minHeight: 64)로 체이닝을 분리해 해결했습니다. 이후 원인 불명 컴파일 에러는 최근에 수정한 한 줄부터 의심하는 습관이 생겼습니다.

03

버전 관리 없이 운영에 이미 배포돼 있던 기능

증상

운동 기록 테이블과 Edge Function이 migration 이력 없이 이미 운영 DB에 존재했습니다.

원인

CI 타입체크 스크립트가 함수 목록을 하드코딩하고 있어서, 나중에 추가된 함수 6개가 조용히 타입체크에서 빠지고 있었습니다.

해결

하드코딩 목록을 deno check supabase/functions/*/index.ts 글롭으로 바꾸고, 기존 스키마를 migration으로 되돌려 버전 관리에 편입시켰습니다.

04

에러 메시지가 클라이언트에서 조용히 사라짐

증상

Google Calendar 미연결 상태로 Agent를 호출하면 사용자에게 아무 안내도 뜨지 않고 그냥 실패했습니다.

원인

서버는 세부 코드를 details.code에 중첩해서 내려줬는데, iOS 에러 파서는 최상위 error.code만 읽고 있었습니다. 문서에는 맞았지만 실제 파싱 코드와는 어긋난 계약이었습니다.

해결

이미 클라이언트가 읽는 최상위 ErrorCode(RESOURCE_NOT_FOUND)로 통일했습니다. 이후 에러 계약은 문서가 아니라 실제 파싱 코드 기준으로 맞추게 됐습니다.

05

모델이 "충돌 없다"고 말해도 믿지 않기

증상

클라우드 Agent가 새 일정을 제안할 때, 모델이 시간 충돌이 없다고 답했는데 실제로는 기존 일정과 겹치는 경우가 있었습니다.

원인

LLM의 자연어 판단을 검증 없이 그대로 실행에 반영하면, 사실과 다른 주장이 그대로 커밋될 수 있습니다.

해결

propose_schedule 호출마다 서버가 기존 일정과의 시간 겹침을 직접 재계산하는 Reflection 단계를 추가해, 모델 주장과 무관하게 서버가 사실을 재확인하도록 했습니다.

06

문서 요약을 믿지 않고 API를 직접 호출해 검증

증상

OpenRouter 모델 allowlist에 넣어둔 모델 일부가 실제로는 더 이상 서빙되지 않는 상태였습니다. 웹 문서 요약은 여전히 최신인 것처럼 그럴듯한 목록을 보여줬습니다.

원인

페이지 요약은 실제 API 응답을 대신하지 않습니다. "문서를 읽었다"가 "지금 이 모델이 존재한다"를 보장하지 않았습니다.

해결

curl https://openrouter.ai/api/v1/models로 원본 JSON을 직접 받아 413개 모델을 확인하고, 실제 서빙 중인 모델만 allowlist에 남겼습니다. 이후 외부 API 스펙은 요약이 아니라 직접 호출로 확인합니다.

07

Reflection이 검사 실패를 "충돌 없음"으로 착각한 fail-open 버그

증상

이 포트폴리오를 검토받던 중 지적받았습니다 — Reflection이 "항상 DB로 재검증한다"고 적어놨는데, 실제로는 그 조회 자체가 실패하면 충돌 없음으로 넘어가는 코드였습니다.

원인

fetchSchedules(...).catch(() => []) — 조회 실패를 빈 배열로 바꿔치기해서, 뒤따르는 충돌 검사가 항상 "겹치는 일정 없음"으로 통과했습니다. fail-closed여야 할 안전장치가 fail-open이었습니다.

해결

조회 실패를 별도 conflictCheckFailed 플래그로 서버→클라이언트까지 끝까지 흘려보내, 실패 시 "충돌 없음"이 아니라 "확인 못 함" 경고를 사용자에게 보여주도록 백엔드와 iOS를 함께 고쳤습니다.

Agent는 온디바이스 우선, 클라우드는 BYOK

B10 · Reflection

모델의 주장을 그대로 믿지 않는다 — 검사 실패도 fail-closed

propose_schedule 호출마다 서버가 기존 일정과의 시간 충돌을 직접 재검사합니다. 모델이 "충돌 없음"이라고 답해도 서버가 다시 확인하고, 그 재검사 자체가 실패하면(예: DB 조회 오류) "충돌 없음"으로 넘기지 않고 확인 실패를 사용자에게 그대로 보여줍니다(트러블슈팅 07).

READ COMMITTED + optimistic version

AI 전용 탭을 없애고 문맥형 Agent 액션으로

Product thesis

Why a calendar, not a chat window

An agent that makes users open an app, start a conversation, and re-explain context ends up unused. Memdo moves the agent to where planning already happens instead.

Early on, this project had a dedicated AI tab. In practice, adding one more tab turned out to be no different from "locking the agent in yet another chat window." So the AI-only page was removed, leaving only contextual agent actions next to Today, Calendar, and Settings (ADR-060) — instead of navigating to a new screen, you get a suggestion directly on the schedule you're already looking at.
One rule protects that direction — completion is never guessed by AI, it only changes through the user's own response at a time the user chose. Recurrence and reminders are complete features without AI; AI is an optional tool for plan drafts, natural-language input, and free-slot search. The agent only ever proposes; writes only happen through the normal API, after the user approves.

Sync flow

Why editing on the subway never loses your changes

The full path an offline change takes to safely converge with the server on reconnect. Split between iOS OutboxQueue.swift and the backend sync Edge Function.

Create, edit, or delete while offline

A failed network request is classified as ScheduleAPIError.offline — the change is never discarded.

The OutboxStore actor queues it to disk

Operations are serialized to JSON and stored locally, in order. The queue survives an app restart.

NWPathMonitor detects reconnection

Network return is delivered as an event, not polled, so there are no wasted retries.

Queue replays in order, reusing the original Idempotency-Key

The key generated when an item was queued is reused, so a duplicate delivery is only ever applied once server-side.

The server checks idempotency and version for conflicts

If another device changed the value first while offline, the server returns 409 instead of letting the client blindly overwrite it.

Only retries worth making stay queued

Still offline: stop right there and leave the rest queued. A request the server actually rejected (a real conflict) gets dropped from the queue, surfaced to the user as an error, and reconciled via refresh() — no infinite retry of a failure that retrying can't fix.

Incremental pull via the (updatedAt, id) cursor

Every following sync call fetches only what changed and delete tombstones — no deep OFFSET.

Troubleshooting

Real problems, actually fixed

More time went here than into the screens. Laid out as symptom → cause → fix.

01

A timezone bug that passed locally but failed in CI

Symptom

The recurrence conflict-check test passed locally (KST) but failed on GitHub Actions (UTC).

Cause

The date functions mixed setHours (local timezone) with toISOString() (UTC). Even after fixing the source, the test fixtures used offset-less strings ('2026-08-16T14:00:00'), reintroducing the same ambiguity.

Fix

Rewrote the date math with Date.UTC() plus an explicit minute offset, and rebuilt the fixtures on top of the real production function, cross-checked under TZ=UTC and TZ=America/New_York.

02

A SwiftUI error the compiler blamed on the wrong line

Symptom

The workout log editor threw a cascading compile error pointing at ForEach and Range<Int> — code I hadn't touched.

Cause

The real cause was one line added just above: .frame(width: 76, minHeight: 64). SwiftUI has no frame overload for that combination, so type inference failed and the compiler blamed an unrelated spot.

Fix

Split it into .frame(width: 76).frame(minHeight: 64). Since then, an unexplained compile error means checking the most recently edited line first.

03

A feature already live in production with no version history

Symptom

The workout-log table and its Edge Function already existed in the production database with no migration history.

Cause

The CI typecheck script hardcoded its list of functions, so six functions added later were silently skipped by typechecking.

Fix

Replaced the hardcoded list with a deno check supabase/functions/*/index.ts glob, and backfilled the existing schema into a migration to bring it under version control.

04

An error that silently vanished on the client

Symptom

Calling the agent while Google Calendar was disconnected just failed silently — no message shown to the user.

Cause

The server nested its detail code under details.code, while the iOS error parser only read the top-level error.code. The docs matched, but the actual parsing code didn't.

Fix

Unified on the top-level ErrorCode (RESOURCE_NOT_FOUND) the client already parsed. Error contracts are now checked against the parsing code, not the docs.

05

Not trusting the model when it says "no conflict"

Symptom

When the cloud agent proposed a new event, it sometimes claimed there was no time conflict when one actually existed.

Cause

Acting on an LLM's natural-language judgment without verification lets a false claim get committed as fact.

Fix

Added a Reflection step: every propose_schedule call has the server independently recompute the time overlap against existing events, regardless of what the model claimed.

06

Verifying against the live API instead of trusting a doc summary

Symptom

Some models in the OpenRouter allowlist had already stopped being served. A web page summary still returned a plausible-looking, seemingly current list.

Cause

A page summary is not a substitute for the actual API response. "The doc was read" doesn't guarantee "this model exists right now."

Fix

Pulled the raw JSON directly via curl https://openrouter.ai/api/v1/models, confirmed 413 models, and kept only the ones actually being served in the allowlist. External API specs are now checked by direct call, never by summary.

07

Reflection's fail-open bug: a failed check read as "no conflict"

Symptom

Caught during a review of this very page — it claimed Reflection "always re-verifies against the DB," but the code silently fell through to "no conflict" whenever that lookup itself failed.

Cause

fetchSchedules(...).catch(() => []) swapped a fetch failure for an empty array, so the conflict check downstream always passed as "nothing overlaps." A safeguard meant to fail closed was failing open.

Fix

Threaded a dedicated conflictCheckFailed flag from the backend through to the client, so a failed check now shows the user an explicit "couldn't verify" warning instead of silently reading as safe — fixed in the backend and iOS together.

Design decisions

7 of 75 ADRs

Every non-obvious choice was recorded as an Architecture Decision Record. Writing the reason down once means never re-litigating "why did we do it this way" later.

ADR-039

Reschedule is a dedicated atomic command

To prevent a partial failure where only the original disappears mid-move, closing the original and creating the replacement happen inside one PostgreSQL function.

ADR-011 / B4

Keyset cursor sync + offline outbox

Incremental pull uses an (updatedAt, id) cursor instead of a deep OFFSET; offline creates/edits/deletes queue locally on iOS and replay on reconnect.

ADR-020

Google events are a separate mirror, not a Todo

External calendar events aren't merged into the Todo table — they're stored in a read-only mirror table that keeps source, permissions, and completion state as separate responsibilities.

ADR-073

On-device agent first, cloud is BYOK

Instead of an always-on server orchestration layer, Apple FoundationModels on-device is the default, and a user's own OpenRouter key unlocks a stronger cloud model on demand. Reusing an existing AI subscription was ruled out — it either has no API access at all, or violates a third-party tool's terms of service.

B10 · Reflection

Never take the model's claim at face value — fail closed on the check itself

Every propose_schedule call has the server independently re-check the time conflict against existing events, even when the model says "no conflict" — and if that re-check itself fails (a DB error), it's surfaced to the user as unverified, never silently treated as "no conflict" (Troubleshooting 07).

ADR-018

READ COMMITTED + optimistic version

At a 50-person pilot's scale, a version-field-based optimistic concurrency model is enough — no need for a heavier isolation level or pessimistic locking.

ADR-060

Removed the AI-only tab for contextual agent actions

Instead of a standalone agent screen, agent actions sit next to Today, Calendar, and Settings, so a suggestion arrives on the current content with no tab switch. The core product decision of this project.

Design system

The first time I built a real design system

Instead of stacking features one at a time, I turned decisions — color, type, motion — into tokens with a written reason, properly, for the first time.

I was used to hand-building custom components, but as screens multiplied, color and motion started getting redecided ad hoc on every screen. So instead of arbitrary values, I started documenting design decisions as reusable tokens (color presets, a type scale, motion durations) with the same rigor as code. Below are decisions that were actually reversed — running a design system for the first time meant learning firsthand that it never converges in one pass.

Engineering practice

Built solo, verified like a team

01

Migrations are the source of truth

No ORM — SQL migrations stay the schema's origin, so RLS, cron, and views are never maintained in two places.

02

RLS, no exceptions

Every user table gets an owner policy keyed on (select auth.uid()); tables that need service-role-only writes (Vault references, rate-limit logs) never get an authenticated write grant at all.

03

AI as a pair programmer, verification stays mine

I designed and built this with Claude Code, but every claim was re-verified against real code or a real API response. For example, an earlier draft of this very page claimed "Google Calendar connects via MCP" — I checked the backend, found no MCP server, and corrected it to "read-only OAuth mirror."
