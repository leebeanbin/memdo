# 문서 변경 및 운영 규칙

## 1. 목적

문서를 설명 자료가 아니라 제품의 실행 가능한 기억으로 유지한다.

## 2. 변경 절차

1. 사용자 문제를 한 문장으로 기록한다.
2. 기존 PRD 또는 ADR로 해결되는지 확인한다.
3. 새 요구사항이면 PRD ID를 부여한다.
4. UX, 개인정보, 데이터, API, 기술, 테스트 영향을 확인한다.
5. 추적성 매트릭스를 갱신한다.
6. 미결정 판단이면 ADR 후보로 기록한다.
7. 구현 후 테스트 증거와 문서 차이를 확인한다.

## 4. 중복 규칙

- 정의는 한 문서에만 둔다.
- 다른 문서에서는 정의를 복사하지 말고 링크와 적용 예만 둔다.
- Todo 상태의 정답은 용어집과 데이터 모델이다.
- 화면 문구의 정답은 UX 문서다.
- API 필드의 정답은 OpenAPI다.
- 개인정보 허용 범위의 정답은 개인정보 정책이다.

## 5. ADR 규칙

다음 경우 ADR을 추가한다.

- 둘 이상의 합리적 선택지가 있음
- 변경 비용이 큼
- 개인정보 또는 보안에 영향
- 여러 문서와 시스템에 동시에 영향
- 나중에 “왜 이렇게 했는가?”가 중요함

ADR 형식:

```text
ID와 제목
상태
맥락
결정
대안
결과와 비용
영향 문서
```

## 6. 버전 규칙

- `0.x`: 제품 검증과 MVP 설계
- `1.0`: 첫 공개 출시 기준선
- 요구사항 삭제는 추적표에서 즉시 지우지 않고 폐기 상태와 이유를 기록한다.
- API 파괴 변경은 OpenAPI 버전과 마이그레이션 계획을 함께 갱신한다.

## 7. 변경 체크리스트

- [ ] 데이터 필드와 상태 전이가 정의됐는가?
- [ ] 개인정보와 잠금화면 노출을 확인했는가?
- [ ] API 계약이 갱신됐는가?
- [ ] 테스트 ID와 출시 기준이 있는가?
- [ ] 추적표가 갱신됐는가?
- [ ] 로드맵 범위가 갱신됐는가?
- [ ] 대표 조회 경로와 인덱스 영향이 확인됐는가?
- [ ] 외부 호출의 타임아웃·재시도·멱등성이 정의됐는가?
- [ ] 데이터 파이프라인과 운영 메트릭이 갱신됐는가?
- [ ] 검색 대상 필드와 개인정보 범위를 확인했는가?
